# FreezeHub — Data Model

## Purpose

This document specifies the logical persistence model required before implementing tenant/catalog persistence (`FZ-011`–`FZ-015`), per `FZ-005`.

It covers `Organization` and the `Catalog` domain module (`Team`, `Application`, `Environment`) as defined in `01-domain.md`.

## Scope

Covered now:

- `organization`
- `users`
- `team`
- `application`
- `team_application`
- `environment`
- `change_restriction` and its three scope tables (added by `FZ-020`)

- `integration` and `notification` (the outbox), added by `FZ-040`
- `api_key`, added by `FZ-052`
- `audit_event`, added by `FZ-060`
- `deployment_check`, added by `FZ-070`
- `subscription`, added by `FZ-081`
- `demo_request`, added by `FZ-083` — **the one table with no `organization_id`**
- `stripe_event`, and `subscription`'s Stripe columns, added by `FZ-084`
- `integration.signing_secret`, added by `FZ-048`

Deliberately deferred, added just-in-time before their own backlog items:

Nothing outstanding — every table specified here exists.

Their purpose and their rules are specified in `11-commercial.md`; committing to a physical schema here would be speculative ahead of the stories that implement them. `demo_request` is worth flagging now for one reason: it is the only table in the system with **no `organization_id`**, because a demo request belongs to no tenant yet. It is read by operators and is never reachable from the tenant API.

**Resolved by `FZ-010`:** the `users` table below carries the subject an external identity provider assigns, per `06-security.md`'s choice of Amazon Cognito for human authentication.

**Renamed by `FZ-132`** (`OI-16`): the column was `cognito_subject` and is now `external_subject`. It never held anything provider-specific — it holds whatever an OIDC issuer put in the `sub` claim — and the backend has no coupling to Cognito at all. The old name asserted one, and a name is the first thing a reader believes.

## Conventions

- Primary keys: `BIGINT` identity columns (`GENERATED BY DEFAULT AS IDENTITY`). Simpler and cheaper to index/join than UUIDs; sequential IDs being guessable is not a tenant-isolation risk here because authorization is never derived from the ID itself — every request's `organization_id` comes from the authenticated context, never from client input (`CLAUDE.md` §5, enforced below under Tenant Isolation).
- Timestamps: `TIMESTAMPTZ`, written/compared in UTC, per domain invariant "time must be persisted and compared using an unambiguous UTC representation" (`01-domain.md`).
- Every tenant-owned table has a non-null `organization_id` foreign key to `organization.id`.
  - **One table is deliberately not tenant-owned: `demo_request` (`FZ-083`).** A demo request predates the organization it might become, so there is nothing to scope it to. Nothing in the tenant API reads it — there is no endpoint that can — and operators read it directly. It is called out here because "the table with no `organization_id`" is exactly the shape a future tenant-isolation bug takes.
- Liquibase changesets for these tables are added per backlog item (e.g. `FZ-011` adds `organization`), not all at once here — this document specifies the target shape, migrations land incrementally.

## Tables

### `organization`

The tenant boundary. Not itself tenant-owned.

```text
id             BIGINT PRIMARY KEY GENERATED BY DEFAULT AS IDENTITY
name           VARCHAR(255) NOT NULL
starting_soon_lead_time_minutes INT NOT NULL DEFAULT 1440   -- 24 hours (FZ-047)
deployment_check_retention_days INT NOT NULL DEFAULT 365    -- one year (FZ-070)
created_at     TIMESTAMPTZ NOT NULL DEFAULT now()
updated_at     TIMESTAMPTZ NOT NULL DEFAULT now()

CHECK (starting_soon_lead_time_minutes BETWEEN 1 AND 43200)
CHECK (deployment_check_retention_days BETWEEN 7 AND 3650)
```

### `users`

Tenant-owned.

```text
id               BIGINT PRIMARY KEY GENERATED BY DEFAULT AS IDENTITY
organization_id  BIGINT NOT NULL REFERENCES organization(id)
external_subject VARCHAR(255) NOT NULL UNIQUE
email            VARCHAR(320) NOT NULL
role             VARCHAR(20) NOT NULL DEFAULT 'MEMBER'
created_at       TIMESTAMPTZ NOT NULL DEFAULT now()
updated_at       TIMESTAMPTZ NOT NULL DEFAULT now()

UNIQUE (organization_id, email)
CHECK (role IN ('ADMINISTRATOR', 'MEMBER'))
```

`role` per `06-security.md`'s minimal role model — gates exactly one action (inviting a user), not general RBAC. Provisioning: an org's first (`ADMINISTRATOR`) user is admin-provisioned out-of-band; subsequent users are added via in-product invite — see `06-security.md`.

### `team`

Tenant-owned.

```text
id               BIGINT PRIMARY KEY GENERATED BY DEFAULT AS IDENTITY
organization_id  BIGINT NOT NULL REFERENCES organization(id)
name             VARCHAR(255) NOT NULL
created_at       TIMESTAMPTZ NOT NULL DEFAULT now()
updated_at       TIMESTAMPTZ NOT NULL DEFAULT now()

UNIQUE (organization_id, name)
```

### `application`

Tenant-owned. Examples per `01-domain.md`: `payments-api`, `checkout-web`, `identity-service`.

```text
id               BIGINT PRIMARY KEY GENERATED BY DEFAULT AS IDENTITY
organization_id  BIGINT NOT NULL REFERENCES organization(id)
name             VARCHAR(255) NOT NULL
created_at       TIMESTAMPTZ NOT NULL DEFAULT now()
updated_at       TIMESTAMPTZ NOT NULL DEFAULT now()

UNIQUE (organization_id, name)
```

### `team_application`

Join table. "An application may be associated with one or more teams" (`01-domain.md`) — modeled many-to-many.

```text
team_id          BIGINT NOT NULL REFERENCES team(id)
application_id   BIGINT NOT NULL REFERENCES application(id)

PRIMARY KEY (team_id, application_id)
```

Invariant (application-layer, not a database constraint): `team_id` and `application_id` must belong to the same `organization_id`. Postgres cannot express "same tenant across two FK targets" as a single constraint without a trigger; this is enforced in the service layer, consistent with `01-domain.md`'s restriction-scope tenant-isolation invariant.

### `environment`

Tenant-owned. Names are organization-owned — no fixed taxonomy is assumed (`01-domain.md`: "FreezeHub must not assume every organization uses the same environment taxonomy").

```text
id               BIGINT PRIMARY KEY GENERATED BY DEFAULT AS IDENTITY
organization_id  BIGINT NOT NULL REFERENCES organization(id)
name             VARCHAR(255) NOT NULL
created_at       TIMESTAMPTZ NOT NULL DEFAULT now()
updated_at       TIMESTAMPTZ NOT NULL DEFAULT now()

UNIQUE (organization_id, name)
```

### `change_restriction`

Tenant-owned. Added by `FZ-020`. Attributes follow `01-domain.md`'s ChangeRestriction.

```text
id               BIGINT PRIMARY KEY GENERATED BY DEFAULT AS IDENTITY
organization_id  BIGINT NOT NULL REFERENCES organization(id)
name             VARCHAR(255) NOT NULL
description      TEXT NULL
reason           TEXT NOT NULL
type             VARCHAR(40) NOT NULL DEFAULT 'DEPLOYMENT_FREEZE'
level            VARCHAR(20) NOT NULL
status           VARCHAR(20) NOT NULL
starts_at        TIMESTAMPTZ NOT NULL
ends_at          TIMESTAMPTZ NOT NULL
created_by       BIGINT NOT NULL REFERENCES users(id)
created_at       TIMESTAMPTZ NOT NULL DEFAULT now()
updated_at       TIMESTAMPTZ NOT NULL DEFAULT now()

CHECK (type IN ('DEPLOYMENT_FREEZE'))
CHECK (level IN ('ADVISORY', 'HARD_FREEZE'))
CHECK (status IN ('SCHEDULED', 'ACTIVE', 'COMPLETED', 'CANCELLED'))
CHECK (starts_at < ends_at)
INDEX (organization_id)
```

Notes:

- `reason` is `NOT NULL`: the product exists to *communicate* restrictions, so a restriction without a stated reason is not useful. `description` stays optional.
- No `UNIQUE (organization_id, name)` — a recurring freeze ("Black Friday Freeze") legitimately reuses a name year over year, and no requirement asks for uniqueness.
- `CHECK (starts_at < ends_at)` mirrors domain invariant 1 at the database level, in addition to service-layer validation.
- `status` omits `DRAFT`, which `01-domain.md` reserves but explicitly defers. Adding it later is a `CHECK`-only migration.
- `type` exists for the extension point the domain describes, but is server-controlled: MVP only ever writes `DEPLOYMENT_FREEZE`.
- `created_by` references the `users` row resolved from the authenticated principal.

### `change_restriction_team` / `change_restriction_application` / `change_restriction_environment`

Scope association tables — one per scope dimension. Real foreign keys per dimension rather than a single polymorphic `(resource_type, resource_id)` table, so referential integrity is enforced by the database.

```text
change_restriction_team
  restriction_id  BIGINT NOT NULL REFERENCES change_restriction(id) ON DELETE CASCADE
  team_id         BIGINT NOT NULL REFERENCES team(id)
  PRIMARY KEY (restriction_id, team_id)
  INDEX (team_id)

change_restriction_application
  restriction_id  BIGINT NOT NULL REFERENCES change_restriction(id) ON DELETE CASCADE
  application_id  BIGINT NOT NULL REFERENCES application(id)
  PRIMARY KEY (restriction_id, application_id)
  INDEX (application_id)

change_restriction_environment
  restriction_id  BIGINT NOT NULL REFERENCES change_restriction(id) ON DELETE CASCADE
  environment_id  BIGINT NOT NULL REFERENCES environment(id)
  PRIMARY KEY (restriction_id, environment_id)
  INDEX (environment_id)
```

Notes:

- Scope rows belong to the restriction aggregate: deleting a restriction cascades them away.
- The **resource** foreign keys deliberately do *not* cascade. Deleting a team/application/environment that a restriction references is refused by the database, because cascading would silently shrink a restriction's scope — potentially emptying it, violating invariant 3, and silently un-freezing deployments.
- The index on each second column supports that foreign-key check, which runs on every catalog delete.
- Tenant isolation across the join is enforced in the service layer (same reasoning as `team_application` above): every scope id is verified to belong to the authenticated organization before insert.
- Matching semantics for these three dimensions are specified in `01-domain.md` § Scope matching semantics.

### `integration`

Tenant-owned. Where an organization's notifications are sent. Added by `FZ-040`.

```text
id               BIGINT PRIMARY KEY GENERATED BY DEFAULT AS IDENTITY
organization_id  BIGINT NOT NULL REFERENCES organization(id)
type             VARCHAR(20) NOT NULL
enabled          BOOLEAN NOT NULL DEFAULT true
config           TEXT NOT NULL
created_at       TIMESTAMPTZ NOT NULL DEFAULT now()
updated_at       TIMESTAMPTZ NOT NULL DEFAULT now()

CHECK (type IN ('SLACK', 'EMAIL', 'WEBHOOK'))
INDEX (organization_id, enabled)
```

Notes:

- `config` is opaque JSON held as text, because each channel needs different settings (a Slack webhook URL, a list of email recipients, a customer endpoint). Giving each channel its own typed columns would mean a migration per channel and a table of mostly-null columns. The **owning channel** interprets it; nothing generic parses it.
- No unique constraint on `(organization_id, type)`: an organization can plausibly notify two Slack channels or several webhooks. Revisit only if a requirement says otherwise.
- `enabled` allows switching a destination off without deleting it and losing its configuration.
- `signing_secret` is the shared HMAC key a webhook receiver uses to verify a delivery came from FreezeHub (`FZ-048`). Nullable: only webhooks have one, and a webhook created before that story has none until it is rotated. It is **not** in `config` deliberately — `config` is customer-supplied and replaceable wholesale, whereas this is generated by FreezeHub, shown once, and must survive a config replacement.
- **Secrets:** a Slack webhook URL is itself a credential, and `signing_secret` is another. Neither can be hashed — the channel needs the URL, and HMAC needs the key — so both are **encrypted at rest** with AES-256-GCM (`FZ-049`, decision `D-3`), stored as `fzenc1:` followed by Base64. A value without that prefix is pre-`FZ-049` plaintext, read as-is and encrypted on its next write.

### `notification`

Tenant-owned. The outbox. One row is **one delivery attempt to one destination**, so a lifecycle event affecting three integrations produces three rows.

```text
id               BIGINT PRIMARY KEY GENERATED BY DEFAULT AS IDENTITY
organization_id  BIGINT NOT NULL REFERENCES organization(id)
restriction_id   BIGINT NOT NULL REFERENCES change_restriction(id) ON DELETE CASCADE
integration_id   BIGINT NOT NULL REFERENCES integration(id) ON DELETE CASCADE
event            VARCHAR(30) NOT NULL
status           VARCHAR(20) NOT NULL DEFAULT 'PENDING'
attempts         INTEGER NOT NULL DEFAULT 0
last_error       VARCHAR(500) NULL
created_at       TIMESTAMPTZ NOT NULL DEFAULT now()
updated_at       TIMESTAMPTZ NOT NULL DEFAULT now()
sent_at          TIMESTAMPTZ NULL

CHECK (event IN ('SCHEDULED', 'ACTIVATED', 'COMPLETED', 'CANCELLED'))
CHECK (status IN ('PENDING', 'SENT', 'FAILED'))
UNIQUE (restriction_id, integration_id, event)
INDEX (status, id)
```

Notes:

- **Per-destination grain.** Slack succeeding while a webhook fails is a normal outcome; one status per event could not express it, and retry (`FZ-044`) has to be per-destination.
- **The unique constraint is the point of the outbox.** It makes enqueueing idempotent: a lifecycle reconciliation that runs twice, or a restart mid-transition, cannot produce a second notification for the same event and destination. Without it, "at least once" delivery quietly becomes "as many times as the worker restarted".
- Rows are written **in the same transaction as the domain change**, which is what makes the intent survive a crash between "restriction activated" and "notification queued" (`02-architecture.md`).
- `event` values are named for what happened rather than reusing `RestrictionStatus`: `ACTIVATED` is an event, `ACTIVE` is a state, and `00-product.md` also lists a "starting soon" notification that is not a status at all.
- `attempts` and `last_error` exist now because a row's whole purpose is to be retried; the retry *policy* is `FZ-044`.
- **`last_error` is bounded at 500 characters, and the rule is what it may contain** (`OI-40`). Every sender composes its own message; none passes a third party's response body through, and the webhook sender reads the response bodiless and reports the exception's class name rather than its message — Spring puts the request URI in that. What made the column unbounded anyway is that `NotificationDelivery` catches every `RuntimeException` and stores `getMessage()` verbatim, so any library's message arrives at whatever length it happens to be. The bound is applied in the entity rather than at each call site, so a writer added later cannot forget it. 500 matches `demo_request.notify_error`, which bounds the same kind of value.
- **Not implemented in `FZ-040`:** the "restriction starting soon" notification `00-product.md` lists. It needs a lead-time decision (how soon is soon) that no document makes, and it is triggered by the passage of time rather than by a transition. Recorded as a gap on `FZ-040`.

### `api_key`

Tenant-owned. Added by `FZ-052`.

```text
id               BIGINT PRIMARY KEY GENERATED BY DEFAULT AS IDENTITY
organization_id  BIGINT NOT NULL REFERENCES organization(id)
name             VARCHAR(255) NOT NULL
key_prefix       VARCHAR(32)  NOT NULL
token_hash       VARCHAR(64)  NOT NULL UNIQUE
created_by       BIGINT NOT NULL REFERENCES users(id)
created_at       TIMESTAMPTZ NOT NULL DEFAULT now()
revoked_at       TIMESTAMPTZ
```

Notes:

- **The raw key is not a column and never becomes one.** Only its SHA-256 hash is stored; the secret exists in one HTTP response and nowhere afterwards (`01-domain.md`, `06-security.md`).
- `token_hash` is `UNIQUE` because it is the authentication lookup: a presented key must resolve to exactly one credential, and therefore to exactly one organization.
- `key_prefix` is the non-secret opening of the key (`fzh_` plus six characters), so a listing can say *which* credential a row is without being enough to use it.
- **No `updated_at`.** Everything about a key is fixed at creation except revocation, which happens once — `revoked_at` is set and never cleared. A revoked key may already be in someone else's hands, so un-revoking it would bring that copy back to life; the remedy is a new key.
- **No `last_used_at`.** It would mean a write on every policy evaluation, which is the hottest path in the product, and no requirement asks for it. Revisit if "is this key still in use?" becomes a real question before revoking one.
### `audit_event`

Tenant-owned. Added by `FZ-060`.

```text
id               BIGINT PRIMARY KEY GENERATED BY DEFAULT AS IDENTITY
organization_id  BIGINT NOT NULL REFERENCES organization(id)
actor_type       VARCHAR(20) NOT NULL      -- USER | SYSTEM | API_KEY
actor_id         BIGINT                    -- null for SYSTEM; no FK, see below
actor_label      VARCHAR(320) NOT NULL
action           VARCHAR(50) NOT NULL
resource_type    VARCHAR(30) NOT NULL
resource_id      BIGINT                    -- null where the action names no stored row
details          TEXT                      -- JSON
occurred_at      TIMESTAMPTZ NOT NULL DEFAULT now()

CHECK (actor_type IN ('USER', 'SYSTEM', 'API_KEY'))
INDEX (organization_id, id DESC)
INDEX (organization_id, resource_type, resource_id)
```

Notes:

- **No foreign key to `users`, deliberately**, and `actor_label` is denormalised. An audit trail that breaks when a user row is removed, or that silently rewrites itself when one is renamed, is not an audit trail. The label is who they were at the time.
- **Immutable by construction**: the entity has no setters and nothing updates or deletes a row. That is enforcement against mistakes, not against someone with database access — the honest limit of storing a trail beside the data it describes.
- `details` is JSON. For an update it is the fields that changed with their before and after values (decision `D-1`); for other actions it is a flat object or null. Always built with Jackson, never by concatenation, because most of what goes in it is user-supplied.
- `resource_id` is nullable because a refused policy evaluation names an application or environment that does not exist.
- The first index serves the trail view, the second serves "what happened to this restriction".
### `deployment_check`

Tenant-owned. Added by `FZ-070`.

```text
id                   BIGINT PRIMARY KEY GENERATED BY DEFAULT AS IDENTITY
organization_id      BIGINT NOT NULL REFERENCES organization(id)
api_key_id           BIGINT                    -- no FK, see below
api_key_label        VARCHAR(255) NOT NULL
application          VARCHAR(255) NOT NULL     -- as supplied, possibly unregistered
environment          VARCHAR(255) NOT NULL
decision             VARCHAR(10) NOT NULL      -- ALLOW | BLOCK
blocked_reason       VARCHAR(20)               -- RESTRICTION | UNREGISTERED; null on ALLOW
matched_restrictions TEXT                      -- JSON, denormalised
actor                VARCHAR(320)              -- supplied; customer PII
reference            VARCHAR(255)              -- supplied; usually a commit SHA
source               VARCHAR(1024)             -- supplied; a pipeline URL
checked_at           TIMESTAMPTZ NOT NULL DEFAULT now()

CHECK (decision IN ('ALLOW', 'BLOCK'))
CHECK (blocked_reason IS NULL OR blocked_reason IN ('RESTRICTION', 'UNREGISTERED'))
INDEX (organization_id, id DESC)
INDEX (organization_id, checked_at)
```

Notes:

- **A check, not a deployment.** FreezeHub sees the question and nothing after it — a pipeline told `ALLOW` may still fail on its own, and one told `BLOCK` may deploy anyway. Reading these rows as deployments would be wrong in exactly the audit they exist to serve.
- **Separate from `audit_event` on purpose.** `FZ-060` excluded ordinary evaluations because one happens per deployment and they would bury the administrative trail. This table has that volume, its own retention, and a different reader.
- `application` and `environment` are stored **as supplied**, not resolved to catalog ids: an unrecognised name is the interesting case and there is no id to point at.
- `matched_restrictions` is denormalised (id, name, level) so the record shows what was true at check time — a restriction can be renamed afterwards.
- No foreign key to `api_key`, and the label is denormalised, for the same reason as `audit_event`: what happens to the credential later must not rewrite history.
- **`actor` and `reference` are customer PII**, arriving on every deployment. They are never logged, and `organization.deployment_check_retention_days` is what bounds how long they are held.
- The second index serves both the purge and "what happened during that freeze".

## Tenant Isolation

Applies to every table above except `organization` itself, per `01-domain.md`'s Core Invariants:

1. Every row belongs to exactly one `organization_id`.
2. A row from one organization must never be visible or usable by another.
3. `organization_id` is derived from authenticated context, never trusted from client-supplied request input.
4. Uniqueness constraints (`name`, `email`) are scoped per-organization, not global.
