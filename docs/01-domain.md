# FreezeHub — Domain Model

## Purpose

This document defines the minimum shared language and business invariants required to implement the MVP consistently.

It is intentionally not a complete DDD specification.

## Core Terms

### Organization

A customer/tenant using FreezeHub.

An organization owns its teams, applications, environments, restrictions, integrations, API keys, and audit history.

### User

A human authenticated within an organization. An `ADMINISTRATOR` or a `MEMBER`; active, or removed (deactivated) and able to be reinstated.

### Team

A group responsible for one or more applications.

### Application

A deployable software component managed by an organization.

Examples:

- `payments-api`
- `checkout-web`
- `identity-service`

An application may be associated with one or more teams.

### Environment

A deployment destination or runtime context.

Examples:

- production;
- staging;
- QA.

Environment names are organization-owned; FreezeHub must not assume every organization uses the same environment taxonomy.

### ChangeRestriction

A time-bounded policy that affects software changes.

The MVP exposes deployment/code freeze behavior, but the domain name remains general enough to support additional restriction types later.

Minimum attributes:

```text
id
organizationId
name
description
reason
type
level
startsAt
endsAt
status
createdBy
createdAt
updatedAt
```

For the MVP:

```text
type = DEPLOYMENT_FREEZE
```

### RestrictionLevel

Determines policy behavior.

#### ADVISORY

A matching deployment remains allowed, but the active restriction is returned in the policy decision.

#### HARD_FREEZE

A matching deployment is blocked.

### RestrictionStatus

Supported lifecycle states:

```text
DRAFT (reserved; not required in first implementation)
SCHEDULED
ACTIVE
COMPLETED
CANCELLED
```

Initial MVP creation can create restrictions directly as `SCHEDULED`.

Lifecycle:

```text
SCHEDULED ──start time──> ACTIVE ──end time──> COMPLETED
     │                      │
     └──── cancel ──────────┴───────────────> CANCELLED
```

`DRAFT` is reserved for future use and should not be implemented unless explicitly requested.

### RestrictionScope

Defines which resources are affected by a ChangeRestriction.

MVP scope targets:

- Environment
- Team
- Application

A restriction may contain multiple scope targets.

#### Scope matching semantics

Specified by `FZ-020`. This is the contract `FZ-051` (policy evaluation) implements; `FZ-020` only persists scope, it does not evaluate it.

Each scope target type is an independent **dimension**. Within a dimension the listed resources are OR'd; the dimensions are AND'd together:

```text
matches(application, environment) =
      (teams        is empty OR application belongs to one of teams)
  AND (applications is empty OR application is one of applications)
  AND (environments is empty OR environment is one of environments)
```

An **empty dimension is a wildcard**, not an empty set — it places no constraint. This is what allows "freeze every deployment to production" to be expressed by naming only an environment. It does not weaken invariant 3 below: a restriction with *no* targets in any dimension is still rejected, so a restriction can never mean "freeze everything, everywhere".

Teams and applications are separate dimensions, so naming both narrows rather than widens: it means "this application, and only when it belongs to this team".

A consequence: a scope naming a team and an application that does not belong to that team matches nothing. This is accepted and deliberately **not** rejected at creation time, because team/application membership is mutable — a scope that matches nothing today may match tomorrow.

Example:

```text
applications = [payments-api, checkout-api]
environments = [production]

=> (payments-api OR checkout-api) AND production
```

### PolicyEvaluation

A request asking FreezeHub whether an action is currently allowed.

Initial action:

```text
DEPLOY
```

Typical context:

```text
organization
application
environment
action
evaluation time
```

### PolicyDecision

The result of PolicyEvaluation.

Minimum semantic result:

```text
ALLOW
BLOCK
```

A decision should also explain which active restrictions contributed to it.

### Integration

Configuration that allows FreezeHub to communicate with an external system.

Initial integration types:

- Slack
- Email
- Webhook

### Notification

A delivery attempt generated by a relevant restriction lifecycle event.

### ApiKey

A machine credential owned by an organization and used by CI/CD clients.

Raw API key secrets must not be stored after creation.

### AuditEvent

An immutable record describing an important action or lifecycle change.

## Core Invariants

### Tenant Isolation

1. Every tenant-owned entity belongs to exactly one Organization.
2. A resource from Organization A must never be visible or usable by Organization B.
3. A restriction scope cannot reference a resource belonging to another organization.
4. Organization identity is derived from authenticated context, not trusted from arbitrary request input.

### Membership

1. An organization always has at least one active `ADMINISTRATOR`. The last one cannot be demoted or removed.
2. Removing a user deactivates them; it does not delete them. What they did stays attributed to them.
3. A user belongs to exactly one organization.

### ChangeRestriction

1. `startsAt` must be earlier than `endsAt`.
2. A newly scheduled restriction cannot already be entirely in the past.
3. A restriction requires at least one scope target.
4. A `COMPLETED` restriction cannot become `ACTIVE`.
5. A `CANCELLED` restriction cannot become `ACTIVE`.
6. A cancelled restriction does not affect policy evaluation.
7. A completed restriction does not affect current policy evaluation.
8. Only active restrictions affect current deployment decisions.
9. Time must be persisted and compared using an unambiguous UTC representation.
10. User-facing time zones are presentation concerns and must not alter stored instants.

### Policy

1. No matching active restriction means `ALLOW`.
2. Matching `ADVISORY` restrictions do not independently block deployment.
3. Any matching active `HARD_FREEZE` means `BLOCK`.
4. Policy decisions should identify relevant matching restrictions.
5. Policy evaluation must be deterministic for the same persisted state and evaluation time.

### Audit

Audit history is append-only from the application's perspective.

## Domain Boundaries

Initial logical modules:

```text
organization
catalog
restriction
policy
notification
integration
audit
```

### Organization

Tenant and user-related concepts.

### Catalog

Teams, applications, and environments.

### Restriction

ChangeRestriction lifecycle and RestrictionScope.

### Policy

Evaluation of restrictions against a proposed deployment.

### Notification

Creation and delivery state of notifications.

### Integration

External channel configuration and machine-facing integrations.

### Audit

Recording important actions.

## Explicit Non-Goals

The domain currently does not model:

- deployment exception requests;
- approvals;
- incidents;
- release trains;
- change tickets;
- application dependency graphs;
- arbitrary policy expressions;
- organization-specific workflow engines.

Do not introduce these concepts until a product requirement explicitly requires them.
